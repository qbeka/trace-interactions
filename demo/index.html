    Details

    Trace replays one list of user actions on two builds of a React component under a controlled clock, and judges each build against written requirements that never look at the other build. When a build fails, Trace deletes actions until only the cause is left.

    The bug on this page is one of the seeded bugs, in a small inspector fixture on a corpus I wrote. The broken build keeps the position of the Inspect button from the first time it opens, so after the window changes size the panel grows from the old spot for about a quarter of a second, and then both builds show the same frame.

    The grid of steps and attempts is the whole reduction. Each column is one of the 26 attempts, and a mark means that step was in it. 6 attempts kept the failure, 5 lost it, 13 could not run and 2 failed in a different way. The last 4 each remove one of the 4 remaining steps, and none of them keeps the failure, which is why Trace stops at 4.

    Run it on your own component

    Mark the elements you care about with data-trace-id, write a scenario that says what the user does and what must stay true, and register both builds in a fixture manifest. Then one command replays the scenario on the two builds and writes a report like the one behind this page.

    pnpm trace fixtures add path/to/fixture.json
    pnpm trace run my.scenario.json --baseline tabs@main --candidate tabs@branch

    The README has the setup, and the scenario guide lists every action and requirement.

    Tuned corpus
    18 of 18 seeded bugs caughtThis corpus is tuned and I wrote it, and a control that compares two traces also finds all 18, so the score says little by itself.
    Against comparison
    Finds no more bugsTrace rejects most legitimate changes and can fail a bug both builds share, which a comparison cannot do.
    Reduction
    18 actions to 2, and 14 to 4The failure on this page is the 14 to 4 session. Reduced failures reproduced in 10 of 10 fresh runs and 0 of 3 baseline runs.
    Random sessions
    2 of 295 sessions flaggedBoth are a real bug in a fixture I had labeled correct, found on a reduced requirement list by the stricter final oracle.

    Limits

    • The corpus is small and I wrote it, so it says nothing about how many real bugs Trace would catch.
    • The holdout ran once on an earlier oracle, and no result tests the final oracle on unseen code.
    • Trace only finds what a scenario reaches, and a requirement it never reaches reads as not exercised.
    • Controlled time does not hold every channel, such as workers and ResizeObserver delivery.
    • Timings are lab numbers from one machine, and they are not INP.
    • Nobody outside this project has used it yet.

    Method

    The frames are screenshots of the real fixture, taken by Trace on a rerun of the saved scenarios and kept only because the rerun recorded the same geometry as the saved report. Overlay, Swipe and Difference blend those screenshots in the browser and change nothing in them. The dashed outlines, the ruler and everything in Geometry are drawn from the rectangles in that report. Playback slows down at the failure and skips the quiet stretches, and the clock always shows the recorded time. The full report, the report after the fix and the limits have the rest.
